# Delegation tokens in hdp

The hadoop cluster offers two authentication methods: `kerberos ticket` and `Delegation TOKEN`. Since we can't use
the kerberos ticket in Windows, so we try to use the `Delegation TOKEN`.

## What is a delegation token

`Hadoop Delegation Tokens` are `lightweight, short-lived authentication credentials` issued by Hadoop master services
(such as the `HDFS NameNode or YARN ResourceManager`) after an initial Kerberos authentication. They solve the
scalability bottleneck of Kerberos in large distributed systems.

For example, If you have a 1,000-node HDFS cluster, and whenever reading an HDFS block, you have to authenticate
directly with a KDC on every worker node. The KDC would immediately crash under the load.

Delegation tokens allow a client to authenticate once with Kerberos, retrieve a token from the Hadoop service,
and pass that token to thousands of worker tasks to access resources on the client's behalf.

## Key properties in a delegation tokens object

There are four key fields exist on every `org.apache.hadoop.security.token.Token`:

- `identifier`: token id opaque to most clients
- `kind`: Specifies the Type of the token (e.g. HDFS_DELEGATION_TOKEN, RM_DELEGATION_TOKEN)
- `service`: Specifies the service this token is valid for (e.g. <host>:<port> or <ip>:<port>)
- `password`: the secret of the token(HMAC of the identifier using the master key), never log or transmit in clear text

### The identifier

The identifier contains the below fields:

| Field          | Description                                                  |
|----------------|--------------------------------------------------------------|
| owner          | User who owns the token                                      |
| renewer        | User allowed to renew the token (often yarn or the job user) |
| realUser       | "Impersonator (proxy user), empty if none"                   |
| issueDate      | Epoch millis when the token was issued                       |
| maxDate        | Epoch millis – absolute maximum lifetime                     |
| sequenceNumber | Unique ID generated by the server                            |
| masterKeyId    | ID of the master key used to sign the token                  |

### The kind string

The common value of the kind string:

| Kind                                             | Service                |
|--------------------------------------------------|------------------------|
| HDFS_DELEGATION_TOKEN                            | HDFS NameNode          |
| RM_DELEGATION_TOKEN                              | YARN ResourceManager   |
| MR_DELEGATION_TOKEN / MAPREDUCE_DELEGATION_TOKEN | MapReduce / JobHistory |
| TIMELINE_DELEGATION_TOKEN                        | YARN Timeline Server   |
| kms-dt                                           | Hadoop KMS             |

> In our java program, we only accept the value `HDFS_DELEGATION_TOKEN`, `RM_DELEGATION_TOKEN`.
>

### The service string

The service string should be in the form of `<fqdn>:<port>` or `<ip>:<port>`.

Instead of building the text object manually, we call the SecurityUtil object to handle all the value validation and
error handling.

```java
SecurityUtil.buildTokenService(new InetSocketAddress(host, port));
```

## How the delegation token works

1. `Initial Kerberos Authentication`: The client (e.g., a user submitting a Spark job) authenticates with the Kerberos
   KDC.

2. `Token Request`: The client contacts the HDFS NameNode (or YARN ResourceManager) over a secure RPC connection and
   requests a Delegation Token.

3. `Token Issuance`: The NameNode generates a token containing
   `user identity, token ID, issue date, max lifetime, and a renewer ID`.
   It signs the token using a secret key known only to the NameNode cluster and returns it to the client.

4. `Distribution to Workers`: The client embeds the delegation token into the application submission package sent to
   `YARN ApplicationMaster`.

5. `Task Execution`: Worker nodes use the token in place of Kerberos credentials to read/write HDFS data or register
   YARN containers.
   The service validates the token using its internal secret key without contacting Kerberos.

6. `Renewal and Cancellation`: The token renewer (often the `ApplicationMaster`) periodically renews the token.
   Once the job completes, the token is explicitly cancelled.

### WebHDFS delegation token generation (Step 2)

When querying the `WebHDFS REST API` for a delegation token (via `GETDELEGATIONTOKEN` endpoint), the user request
requires `Kerberos/SPNEGO` authentication. The NameNode generates the token, serializes it, and returns a JSON payload
containing an `URL-safe Base64-encoded string`.

For example:

```shell
# user request
curl --negotiate -u : "http://namenode:50070/webhdfs/v1/?op=GETDELEGATIONTOKEN&renewer=hdfs"

curl --negotiate -u : "https://deb13-spark1.casdds.casd:50470/webhdfs/v1/?op=GETDELEGATIONTOKEN&renewer=hdfs"

# the API Json response
{
  "Token": {
    "urlString": "JQAIaG9y...[Base64 URL-safe String]..."
  }
}

# this token can be reused to authenticate subsequent WebHDFS REST calls without needing Kerberos SPNEGO ticket renewal
# for example use can access data in hdfs with the token.
curl "http://namenode:50070/webhdfs/v1/user/hdfs/data.csv?op=OPEN&delegation=JQAIaG9y..."
```

> The key field in the JSON is `urlString`. This value is the `Base64-encoded delegation token`, which we need to parse
> and store. For Spark applications, these tokens must be serialized into a standard binary file defined by
`HADOOP_TOKEN_FILE_LOCATION`

## Some default values of the token

| Attribute        | Default Value   | Description                                                                 |
|------------------|-----------------|-----------------------------------------------------------------------------|
| Renewal Interval | 24 Hours        | How often a token must be actively renewed before expiring                  |
| Max Lifetime     | 7 Days          | The maximum hard cap lifespan of a token; cannot be renewed past this point |
| Validation       | Local HMAC-SHA1 | Services validate tokens using shared master secrets—zero KDC traffic       |
